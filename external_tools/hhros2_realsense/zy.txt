
## 3.2 D435i 相机 SDK 与 ROS2 开发

本节按“环境准备—节点启动—参数配置—数据采集—日志排查”的顺序组织，目标是让开发和部署人员在不阅读全部源码的情况下，能够完成 D435i 相机的软件安装、ROS2 节点启动、运行时参数调整、图像采集录制、日志读取以及硬件自检等工作，并形成一套可直接复用的工具链。该文档主要覆盖部署与使用层，不展开底层驱动实现和 `realsense2_camera` 包内部源码分析。   

### 3.2.1 开发目标与边界

本节开发内容面向 Intel RealSense D435i 相机在 Ubuntu + ROS2 环境下的工程化使用，主要目标包括：完成 `librealsense` SDK 的安装与验证，完成 `realsense-ros` 功能包的源码编译与启动，支持彩色图像、深度图像、红外图像及相关话题的发布，支持运行时曝光、增益、激光功率、白平衡等常用参数调整，支持拍照、录像、日志记录和日志回读，并提供统一入口菜单以降低日常调试成本。该部分不涉及相机底层固件修改，也不涉及 ROS2 驱动源码的二次开发。根据 README 的用途说明，`start.sh` 负责交互式选择启动参数并生成相机启动行为日志；其具体内部实现未在本次材料中提供。  

### 3.2.2 功能组成与脚本拓扑

该开发工具集由六类功能脚本构成：相机启动脚本 `start.sh`、运行时调参与话题打印脚本 `camera_menu.py`、拍照与录像脚本 `record.py`、启动日志读取脚本 `camera_log_read.py`、相机硬件自检脚本 `camera_test.py`，以及统一入口菜单脚本 `realsense_toolbox_menu.py`。其中，统一入口菜单提供“启动相机”“运行时调参 + Topic 打印”“拍照/录像”“查看日志”“硬件直连测试”“Quick Check”六项功能，并通过子进程方式调用其他工具脚本，因此它相当于整个工具链的总入口。

从功能关系上看，`camera_menu.py` 和 `record.py` 都依赖于 ROS2 相机节点已启动这一前提；`camera_test.py` 则不依赖 ROS2，而是通过 `pyrealsense2` 直接访问设备，更适合在节点启动前做硬件连通性检查；`camera_log_read.py` 用于在排障时快速读取最近一次启动日志；`realsense_toolbox_menu.py` 则把上述能力统一整合起来，便于现场调试和普通用户使用。    

### 3.2.3 环境依赖与文件约定

该套工具的运行环境包括 Ubuntu 系统、ROS2 发行版环境、`librealsense2` SDK、`realsense-ros` 功能包，以及 Python 侧的 `rclpy`、`cv_bridge`、`opencv-python`、`numpy` 和 `pyrealsense2` 等依赖。`record.py` 使用 ROS2 订阅 `sensor_msgs/Image` 消息并借助 `CvBridge` 转为 OpenCV 图像；`camera_test.py` 直接通过 `pyrealsense2` 创建 `pipeline` 和 `config`，启用彩色、深度和红外流；`camera_menu.py` 则通过调用 `ros2 param` 和 `ros2 topic` 命令实现运行时配置和话题查看。  

日志与输出文件统一放在用户目录下的 `~/.ros/log` 附近。`camera_log_read.py` 默认在 `~/.ros/log` 下递归搜索 `realsense_start_YYYY-MM-DD_HH-MM-SS.log` 命名格式的启动日志，并读取最新文件；`record.py` 也会把拍照、录像及录制控制日志写到 `~/.ros/log`；统一菜单脚本还特别提示不要以 root 直接运行，否则 `$HOME` 可能变为 `/root`，进而导致日志路径与普通用户环境不一致。  

### 3.2.4 SDK 与 ROS2 安装部署

根据 README，系统首先需要完成 `librealsense2-dkms`、`librealsense2-utils`、`librealsense2-dev` 等包的安装，并通过 `realsense-viewer` 验证 SDK 是否可正常识别设备。随后在 ROS2 工作空间中克隆 `realsense-ros` 仓库，完成依赖安装、`colcon build` 编译和环境加载。对于日常开发，建议在 `~/.bashrc` 中补充 ROS2 与工作空间的 `source` 语句，以避免每次手工加载环境。你给的 README 中也明确给出了 `rs_launch.py` 与带分辨率参数的启动示例，因此这一部分可以直接作为部署操作步骤使用。

### 3.2.5 标准启动步骤

标准使用流程建议分为五步执行。第一步，完成相机硬件连接，并优先使用 USB 3.0 数据线；第二步，加载 ROS2 与工作空间环境；第三步，使用 `ros2 launch realsense2_camera rs_launch.py` 或 `./start.sh` 启动相机节点；第四步，在新的终端中启动统一工具菜单或单独运行功能脚本；第五步，按任务需要执行参数调整、拍照录像、日志查看或硬件测试。由于 `camera_menu.py` 中固定检查的节点名称为 `/camera/camera`，`realsense_toolbox_menu.py` 的 Quick Check 也会检查该节点，因此现场部署时应保证当前启动命名空间与脚本预期一致。 

需要特别注意的是，你的 README 中给出的参考话题名多为 `/camera/color/...` 风格，而 `record.py` 实际订阅的是 `/camera/camera/color/image_raw` 和 `/camera/camera/depth/image_rect_raw`，说明当前脚本默认基于带二级命名空间的相机节点运行。因此联调时应以现有代码中的节点名和话题名为准，而不能只按 README 里的参考命名机械套用，否则容易出现“节点已启动但脚本收不到图像”的问题。 

### 3.2.6 运行时工作机制

`camera_menu.py` 的职责是对已启动的相机节点做运行时参数配置和话题数据查看。脚本内部首先检查 `/camera/camera` 是否存在，然后提供两类菜单：一类是相机参数调整，另一类是 ROS2 Topic 列表与数据打印。参数调整部分覆盖深度模块和 RGB 相机的典型可调参数，包括自动曝光、手动曝光、增益、激光功率、发射器开关、自动白平衡和白平衡值等；脚本通过 `ros2 param get` 获取当前值，再通过 `ros2 param set` 下发新值，因此属于轻量级运行时控制工具。

`record.py` 的职责是完成拍照和录像。它内部创建 ROS2 节点 `realsense_recorder`，订阅彩色图像和深度图像消息，并缓存最近一帧数据。拍照时，脚本会在等待图像到达后按时间戳保存 RGB 图像和深度图像；录像时，脚本先根据最近接收到的帧估计图像尺寸和帧率，再用 OpenCV 的 `VideoWriter` 写出视频文件。该脚本同时支持对图像做轻度或中等程度降噪，并把拍照、开始录像、停止录像等行为追加写入日志文件。

`camera_test.py` 用于脱离 ROS2 节点做底层硬件连通性自检。脚本首先枚举 RealSense 设备，判断是否存在深度传感器、RGB 传感器和可能的红外传感器，然后直接启动 `pipeline`，尝试打开彩色流、深度流以及两个红外流，并在预热后抓取一帧进行有效性检查。这一机制适合在“硬件已接好但 ROS2 无法正常发布话题”时先做底层排查。

`camera_log_read.py` 用于查看最近的启动日志。它会在 `~/.ros/log` 下递归搜索符合命名规则的日志文件，并按文件名中的时间戳排序，默认读取最新日志；也支持通过 `-f` 指定具体日志文件，或通过 `-l` 指定日志根目录。因此它适合作为启动异常、参数选择历史回溯和运行记录核查的辅助工具。

### 3.2.7 接口描述

#### A. 工具入口接口

统一入口为：

```bash
python3 realsense_toolbox_menu.py
```

该脚本提供 6 个一级功能入口：启动相机、运行时调参与 Topic 打印、拍照/录像、查看最新或指定启动日志、直连硬件测试、Quick Check。Quick Check 会检查 `ros2` 命令是否可用、相机节点 `/camera/camera` 是否存在、最近的 `realsense_start_*.log` 日志是否存在。

#### B. 运行时参数接口

`camera_menu.py` 当前支持的典型运行时参数包括：
`depth_module.enable_auto_exposure`、`depth_module.exposure`、`depth_module.gain`、`depth_module.laser_power`、`depth_module.emitter_enabled`、`rgb_camera.enable_auto_exposure`、`rgb_camera.exposure`、`rgb_camera.gain`、`rgb_camera.enable_auto_white_balance`、`rgb_camera.white_balance`。脚本内部已经给出了参数类型、用途说明和推荐范围，因此可以直接作为运行中调参界面使用。

#### C. 采集与日志接口

拍照录像脚本入口为：

```bash
python3 record.py
```

日志读取脚本入口为：

```bash
python3 camera_log_read.py
python3 camera_log_read.py -f <日志文件路径>
python3 camera_log_read.py -l <日志根目录>
```

硬件自检脚本入口为：

```bash
python3 camera_test.py
```

这些接口分别对应图像采集、日志查看和底层设备检测三类常用开发操作。  

#### D. 话题接口

当前源码中与采集直接相关的核心话题为 `/camera/camera/color/image_raw` 和 `/camera/camera/depth/image_rect_raw`，前者用于 RGB 图像获取，后者用于深度图像获取。`camera_menu.py` 则不写死话题列表，而是在运行时通过 `ros2 topic list` 列出当前所有话题，并允许用户选择某一话题执行 `echo`。因此，若后续相机命名空间调整，只要订阅端与实际发布端保持一致，该工具仍可继续使用。 

### 3.2.8 数据格式与文件命名约定

系统当前的数据落盘格式较为明确。拍照时，RGB 图像保存为 `rgb_photo_时间戳.jpg`，深度图像保存为 `depth_photo_时间戳.png`；录像时，RGB 视频保存为 `rgb_video_时间戳.avi`，深度视频保存为 `depth_video_时间戳.avi`；启动日志采用 `realsense_start_YYYY-MM-DD_HH-MM-SS.log` 命名格式；录制控制行为也会追加写入日志文件。由于这些文件均位于 `~/.ros/log` 相关目录下，因此建议在正式部署时定期清理旧日志和媒体文件，避免目录持续膨胀。 

### 3.2.9 典型使用流程

典型开发流程建议如下：先在 ROS2 节点启动前运行 `camera_test.py`，确认设备、序列号、彩色/深度/红外传感器状态是否正常；然后启动 `realsense2_camera` 节点或 `start.sh`；接着运行 `realsense_toolbox_menu.py` 做 Quick Check，确认环境、节点和日志均正常；若需要现场调参，则进入 `camera_menu.py` 修改曝光、增益、激光功率或打印相关话题；若需要采集实验数据，则运行 `record.py` 进行拍照或录像；若出现启动失败或参数异常，则使用 `camera_log_read.py` 回读最近日志。整个流程从硬件检测、节点启动、运行调参到数据记录形成了相对完整的闭环。    

### 3.2.10 常见问题与故障定位

第一类问题是 ROS2 环境未加载，表现为脚本提示找不到 `ros2` 命令或无法列出节点，这时应先检查 `source /opt/ros/<distro>/setup.bash` 和工作空间环境是否已加载。第二类问题是相机节点已经启动，但脚本无法找到 `/camera/camera`，这通常说明命名空间与当前脚本预设不一致，需要统一 launch 文件和脚本中的节点命名。第三类问题是 `record.py` 在等待 5 秒后仍收不到图像，常见原因包括节点未真正启动、话题命名不一致或订阅目标错误。第四类问题是硬件已接入但仍未被检测到，此时可优先使用 `camera_test.py` 做直连测试，并检查 USB 3.0 数据线和重新插拔情况。第五类问题是日志文件位置与预期不一致，尤其在 `sudo` 或 root 环境中更常见，因为日志可能被写入 `/root/.ros/log`；统一菜单脚本已经对此给出提示。  

### 3.2.11 小结

综上，该 D435i 相机开发工具链已经形成“SDK 安装—ROS2 驱动启动—运行时调参—图像采集—日志排查—统一菜单管理”的完整开发闭环。其中，`camera_menu.py` 解决运行中接口配置与数据查看问题，`record.py` 解决采集留存问题，`camera_log_read.py` 解决日志回溯问题，`camera_test.py` 解决硬件自检问题，`realsense_toolbox_menu.py` 解决多脚本分散使用的问题。若后续补充 `start.sh` 源码，还可以进一步把“启动参数选择—launch 指令生成—日志写入”部分写成更细的源码级开发说明。
